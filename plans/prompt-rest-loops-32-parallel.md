# Промпт: REST-петли — 32 параллельных, без пауз, только собираемое

Репозиторий `blyn-ai/CryptoSmith-X`, .NET 10, сборка только `~/.dotnet/dotnet`
(`global.json` пинит SDK), `TreatWarningsAsErrors`. Solution-level `dotnet test` виснет —
запускать по проектам. Raw SQL + Dapper; Dapper заполняет positional-record **по порядку и
по точному типу** — не заводить record'ов под SELECT, читать кортежами/словарями.

## Задача одним абзацем

Четыре REST-петли хаба и три «трикл»-фида в коннекторах ходят к биржам по одному символу за
раз, с зашитыми паузами, и часть из них обходит весь список биржи вместо собираемого.
Замерено на живых площадках: раунд из **32 параллельных запросов укладывается в 0,8–1,0 с**,
WEEX режет на ~37 req/s по окну (бан ~10 с), Binance выдержал 512 запросов при 64
параллельных без единого отказа. За 6 часов на тесте — **ноль 429** у всех четырёх площадок.
Сделать так, чтобы петли ходили **32 параллельно, без фиксированных пауз, только по
`collect = true`**, с единственным ограничителем — `VenueGate` — и чтобы каждый проход
укладывался в констрейнт владельца: **всё, что дольше секунды на раунд — не годится.**

## Что есть сейчас — по коду, не по памяти

Ограничитель — `src/CryptoSmithX.MarketData.Connectors/Pacing/VenueGate.cs`: минимальный
интервал `1/requestsPerSecond` между стартами + `SemaphoreSlim(maxConcurrentRequests)`,
`AcquireAsync` → `VenueLease`, `Penalize()` на 429 (10 с по умолчанию, `Penalize(TimeSpan)` есть,
`Retry-After` не читается). Один гейт на venue, разделяется всеми петлями и фидами.
Значения — из таблицы `exchange` (`DbSettings.cs:79-80`), на тесте сейчас:

| venue | request_budget_per_s | max_concurrent_requests | source |
| --- | ---: | ---: | --- |
| binance | 16 | 8 | documented |
| weex | 200 | 8 | documented — **число ни в одном из двух источников, на которые ссылается, нет** (`plans/exchange-roadmap.md`) |
| kraken | 20 | 8 | assumed |
| hyperliquid | 10 | 4 | assumed |

Петли (`src/CryptoSmithX.MarketData.Hub/Ingestion/`):

- **`FundingCollector.cs:74-125`** и **`CandleCollector.cs:76-100`** — `foreach` по целям с
  `await` внутри: строго последовательно, параллельности нет вовсе; гейт берётся на каждый
  вызов, 429 → `Penalize()`, один сломанный символ не валит проход. Цели уже фильтруются
  `i.collect = true` (Funding:35, Candle:37) — тут менять только форму цикла.
- **`DepthCollector.cs:82-197`** — уже правильно: `SweepAsync(items, _gate.MaxConcurrentRequests, …)`
  — ограниченно-параллельный обход с fail-fast и одной write-lane в базу. **Это образец;
  Funding и Candle переводятся на него**, а не на свою реализацию.
- **`SnapshotCollector.cs`** — тикеры приходят одним bulk-вызовом, петля по ответу, не по
  бирже; здесь параллелить нечего. Медленное в снапшоте — OI-фиды ниже.
- **Трикл-фиды с собственными паузами поверх гейта** — три файла, три зашитых `Task.Delay`:
  - `Connectors/Binance/BinanceOpenInterestFeed.cs:34` — `Pace = 400 ms` («2,5 req/s, ~570
    символов за ~4 минуты»); символы берёт из `exchangeInfo` биржи (`RefreshSymbolsAsync`,
    :163) — **все 566 trading, при 44 собираемых**.
  - `Connectors/Weex/WeexOpenInterestFeed.cs:119` — `Pace` 150 ms; символы из
    `GetContractsAsync` (:145) — **все ~990, при 25 собираемых**; `MaxAge = 10 мин` (:32) при
    проходе ~7 мин — запас 1,4×, вырастет проход на треть — OI начнёт пропадать со страницы.
  - `Connectors/Hyperliquid/HyperliquidBookFeed.cs:27` — `Pace = 800 ms`; символы из
    `meta.Universe` (:150) — **все 178, при 25 собираемых**.

Измеренные проходы на тесте за 6 ч (`collector_run`, `exchange_instrument_id is null`):

| | kraken | binance | weex | hyperliquid |
| --- | ---: | ---: | ---: | ---: |
| funding, avg / max | **74 / 100 с** (206 символов) | 18 / 26 | 9 / 11 | 12 / 19 |
| candles | **33 / 84 с** (715 баров) | 16 / 36 | 9 / 17 | 10 / 27 |
| depth | 16 / 63 с (275) | 3 / 10 | 0,4 / 8 | 3 / 7 |
| snapshot | 1,7 / 29 | 2,0 / 9 | 1,6 / 9 | 1,0 / 7 |

Kraken funding: 206 вызовов за 74 с — ~360 мс на вызов, строго по одному. При 32
параллельных это ~2,5 с на весь проход, при том же темпе на вызов.

## Что сделать — по шагам, в этом порядке

**0. Замерить, прежде чем менять** (правило проекта: ни одной правки без измерения за ней).
WEEX и Binance измерены — числа выше, повторять не надо. **Kraken Futures и Hyperliquid — не
измерены.** Тем же скриптом, что мерили WEEX/Binance (форма пробы: `N параллельных × пауза ×
раундов`, конфигурация **32 × 0,5 с × 16**, публичный per-symbol эндпоинт, который и ходит в
петле — для Kraken `/derivatives/api/v3/history` или тот, что зовёт `GetFundingHistoryAsync`,
для HL `info` с `l2Book`/`candleSnapshot`), снять: сколько 200, сколько 429/отказов, время
раунда, длина бана, если сорвался. Kraken отдаёт троттлинг **телом при HTTP 200** — проверять
`error`, не статус. Результат — в заголовок коммита и в `plans/collection-policy.md` §5
(«Измеренное, чтобы не мерить заново»). Цифру лимита, полученную повторением **одного** URL,
считать несуществующей (край отдаёт из кеша) — символы в раунде должны быть разными.

**1. Посев бюджетов — `measured`, не `documented`.** Одна миграция `0036_measured_budgets.sql`
(следующий свободный номер проверить по `Migrations/`; применённые файлы не правятся):
`update exchange set request_budget_per_s = …, max_concurrent_requests = 32,
request_budget_source = 'measured'`. Значения: WEEX — **30** (измерено 37, запас ~20 %, окно);
Binance — по весу: 2400 weight/мин у USDM = 40/с при весе 1, фид OI весит 1, свечи — 1..10 по
`limit`; ставить **32** и объяснить в заголовке, почему не 40; Kraken и HL — из шага 0, с тем
же запасом ~20 %. Заголовок миграции — как во всех предыдущих: развёрнуто, с числами и
откуда они. `request_budget_source` умеет `measured` с 0021, но ни одна строка так не
помечена — это первая.

**2. Funding и Candle → `SweepAsync`.** Вынести `DepthCollector.SweepAsync` в общий файл
(`Ingestion/Sweep.cs`, `internal static`) без изменения поведения, перевести на него оба
`foreach`. Параллельность — `_gate.MaxConcurrentRequests`, ничего локального. Запись в базу
через ту же одну write-lane, как в Depth (одно соединение, `SemaphoreSlim(1,1)`), — **не**
открывать соединение на рабочий. Семантика ошибок сохраняется: один символ упал — считаем,
идём дальше; все упали — проход упал. Fail-fast в Depth — на 429 весь проход останавливается
и гейт наказан; перенести как есть.

**3. Трикл-фиды — паузы убрать, список сузить.**
- `Pace` в трёх фидах удалить; единственный темп — `_gate.AcquireAsync`. Комментарий в
  Binance-фиде («этот фид добровольно берёт 2,5 req/s из общего бюджета») описывает
  правильную идею неправильным механизмом: делёж бюджета между фидами — это будущий
  `collection-policy.md`, не зашитая константа. Сейчас гейт — общий, и это всё.
- Символы фидов — **из нашей базы, `collect = true and status = 'trading'`**, а не из списка
  биржи. Как это дотащить в коннектор: фиды строятся в `ExchangeWorker.Build*` (:531-660),
  там есть `Db`; передать `Func<CancellationToken, Task<string[]>>` вместо
  `RefreshSymbolsAsync` по бирже. `SymbolRefreshInterval` (10 мин) оставить — это про то, как
  часто перечитывать список, не про темп запросов.
- `MaxAge` у WEEX (10 мин) и Binance (15 мин) оставить — после сужения списка проход 25
  символов займёт секунду, запас станет сотни ×; менять число незачем.
- Обход символов внутри фида — тем же `SweepAsync` (он `internal` в хабе; фиды в
  Connectors — либо вынести `Sweep` в `Connectors/Pacing/`, либо сделать фид получателем
  делегата обхода. Первое проще и честнее: обход — часть pacing).

**4. Retry-After.** В `Penalize()`-ветках трёх петель и трёх фидов: если у
`HttpRequestException` есть ответ с `Retry-After`, звать `Penalize(TimeSpan)` с ним; иначе —
как сейчас. `VenueGate` не менять.

**5. Записать измеренное.** Пойманный 429 сегодня никуда не пишется. Минимум: в
`collector_run` уже есть `http_status` и `request_weight` — убедиться, что 429 из
`SweepAsync` туда доезжает с `http_status = 429` (сейчас per-item ошибки схлопываются в
`failed`). Больше — не надо; запись `measured` обратно в `exchange` по факту 429 — это
`collection-policy.md`, не этот PR.

## Чего НЕ делать

- **Не трогать архитектуру**: никакого каскада global/venue/dataset, никакой параллельности
  в `dataset_setting`, никакой истории изменений. Это `plans/collection-policy.md`, отдельно.
- Не переписывать `VenueGate` (кроме чтения `Retry-After` снаружи). Не добавлять второй
  ограничитель.
- Не трогать WS-путь (`*WsFeed`, `*BookBuilder`), Binance WS — отдельная незакрытая проблема.
- Не менять `SnapshotCollector` — он bulk. Provenance-колонки 0030/0033/0035 — следующий
  шаг, не этот. Не писать в новые таблицы 0032.
- Не писать «100500 тестов». Достаточно: тест на `Sweep` (параллельность ≤ N, fail-fast,
  один упавший не валит остальных — он, возможно, уже есть у Depth, тогда переехать с ним) и
  тест, что фиды берут символы из делегата, а не из клиента биржи.
- Не менять поведение при 0 целей и при «все упали».

## Приёмка — числами, с живого теста

Тот же запрос к `collector_run` за 6 часов **после** деплоя на тест, рядом с таблицей выше:

- каждый проход funding/candles/depth у каждой площадки — avg ≤ **3 с**, max ≤ 10 с
  (Kraken funding: было 74 с);
- **429 за 6 ч = 0** у всех четырёх, как и было — ускорение не купило отказов;
- OI-фиды: полный проход по собираемым ≤ 5 с (в логе фида есть длительность прохода —
  если нет, добавить одну строку `Information` на проход: символов, секунд, отказов);
- `exchange.request_budget_source = 'measured'` у всех четырёх;
- у Kraken и HL в `plans/collection-policy.md` §5 появились измеренные числа с датой.

Если какой-то из проходов после правки **длиннее** секунды на раунд из 32 — это не «ну
ладно», это не сделано: найти, где ждём (гейт? база? сама биржа?), и назвать слой.

## Деплой

пушем, если их трогали (не должны). Миграция применится мигратором при старте.
