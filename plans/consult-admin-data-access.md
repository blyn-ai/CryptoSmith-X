# Консультация: админка ходит в базу напрямую или через API?

Нужен разбор архитектурного решения. Ниже — контекст, два подхода и замеренные
факты. Просьба не подстраиваться под ожидаемый ответ: если один из вариантов
явно хуже, так и сказать.

---

## 1. Что за система

Платформа сбора рыночных данных по бессрочным фьючерсам. .NET 10, PostgreSQL 16.
Три исполняемых проекта:

| Проект | Размер | Роль |
|---|---|---|
| `Hub` | воркер, без HTTP | Опрашивает биржи (Kraken, WEEX, Hyperliquid), пишет в БД. Снапшоты каждые 10 с, свечи и глубина раз в минуту, деривативные таймфреймы. |
| `WebApp` | ~3 900 строк C# + Razor | Админская консоль (server-rendered MVC), плюс публичная входная страница, плюс приёмник событий от ботов `/api/ingest/events`. |
| `Api` | 432 строки | Пять читающих эндпоинтов `/v1`: health, exchanges, instruments, snapshot, candles. Публичные рыночные данные для внешних потребителей. |

Сознательные конвенции проекта, менять их не предлагать без веской причины:
**сырой SQL через Dapper + Npgsql, без EF, без репозиториев, без слоя
абстракций над БД.** Схема — источник истины, миграции нумерованными SQL-файлами.
`TreatWarningsAsErrors`. Разработчик по факту один.

Объём данных: 1482 инструмента, ~1.8 млн строк свечей в сутки, база 1.7 ГБ и
растёт на ~560 МБ в сутки.

## 2. Как админка работает сейчас

`WebApp` обращается к PostgreSQL напрямую:

* ~94 SQL-запроса, разложенных по «сторам»: `ExchangeStore` 30, `InstrumentStore`
  16, `DashboardStore` 15, `AssetStore` 12, остальные меньше;
* один рендер главной страницы дашборда — **7 обращений к БД**, страница сама
  обновляется **каждые 10 секунд**;
* `LiveNotifier` держит **постоянное выделенное соединение** с
  `LISTEN csx_live` (Postgres NOTIFY) и раздаёт события в браузер через SSE;
* при старте `Migrator.VerifyAsync` — приложение **отказывается подниматься**,
  если схема отсутствует или отстала от кода;
* запросы операционные и широкие: соединения `collector_status` × `exchange` ×
  `market_snapshot_latest`, оконные функции, агрегаты по партициям.

## 3. Что заставило задуматься

Появляется вторая площадка. Прод стоит на своём VPS. Новый стенд — виртуалка в
сети клиента, туда едут Hub и своя база. Возник вопрос, можно ли админку держать
у себя, а базу у клиента. Замеренная задержка между площадками (два плеча
WireGuard):

```
своя площадка → хаб клиента:    avg 18.6 ms   (min 1.1,  max 66.6,  разброс 25)
хаб клиента   → виртуалка:      avg 53.4 ms   (min 31.4, max 108.9, разброс 29)
```

То есть ~50–70 мс на круг с сильным джиттером. Семь последовательных запросов на
рендер — около 0.4 с чистой сети на страницу, каждые 10 секунд, плюс постоянное
`LISTEN`-соединение через два туннеля и старый роутер (100 Мбит) на стороне
клиента.

**Важная оговорка, чтобы не отвечать не на тот вопрос.** У этой конкретной боли
есть дешёвое решение: перенести админку на ту же виртуалку, где база, и смотреть
её через существующий VPN. Оно ничего не стоит — админка и так контейнер в том же
compose-стеке. Вопрос ниже — не «как починить сегодня», а стоит ли менять
архитектуру на длинной дистанции.

## 4. Подход A — оставить как есть

Админка продолжает ходить в PostgreSQL напрямую. Правило развёртывания:
**консоль всегда живёт рядом со своей базой**. Публичный API развивается
отдельно, для внешних потребителей, и админка им не пользуется.

## 5. Подход B — админка только через HTTP API

`WebApp` теряет доступ к БД. Все данные — через `Api`, который становится
единственным, кто говорит с PostgreSQL (кроме `Hub`, который пишет). Админка
превращается в клиента собственного API.

## 6. Что известно и относится к делу

Факты, а не аргументы:

* 94 места с SQL превратятся в эндпоинты + DTO + клиентский код. Часть запросов
  специфична ровно для одной страницы (дашборд, детали инструмента, страница
  актива с алиасами).
* Дашборд делает 7 запросов на рендер. Через API это 7 HTTP-вызовов, каждый из
  которых делает свой запрос к БД.
* SSE сейчас питается напрямую от `LISTEN/NOTIFY`. Через API это становится
  ретрансляцией: API слушает Postgres, админка слушает API.
* Админка не только читает — она пишет: правит настройки бирж и коллекций,
  алиасы активов, включает и выключает сбор. Сейчас это прямые `update` из Razor-
  контроллеров.
* В планах мультиарендность (несколько клиентов, свои боты и журналы) — сегодня
  таблицы `tenant` и `bot` существуют, но пусты.
* Публичный API как продукт всё равно нужен: он в дорожной карте как отдельный
  продаваемый слой.
* Разработчик один. Любое удвоение объёма кода — это реальная цена, а не
  абстракция.

## 7. Вопрос

1. Какой подход выбрать и почему? Если ответ «зависит» — от чего именно, и какой
   наблюдаемый признак означает, что пора переходить к B?
2. Есть ли третий вариант, который лучше обоих? Например: админка на прямом SQL,
   но с жёстким правилом co-location; или разделение по операциям (чтение через
   API, запись напрямую, или наоборот); или вынос части ответственности из
   `WebApp`, который сегодня совмещает три разные роли — консоль, публичную
   страницу и приёмник событий от ботов.
3. Что в подходе B недооценивают чаще всего — то, что выясняется уже после того,
   как переписали?
