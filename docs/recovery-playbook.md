# Аварии и добивка данных

Что делать, когда часть данных не записалась или записалась неправильно. Держим
здесь, а не в головах: авария повторяется через месяцы, а решение принимается за
пять минут и не тем человеком.

Главное правило сверху: **сначала записать, что именно потеряно, потом решать,
чинить ли**. Дырка, про которую известно, честнее ряда, залатанного догадкой.
Незаполненные дырки перечислены в конце файла — этот список ведём.

---

## 1. Что вообще можно добить

| Данные | Источник для пересчёта | Можно добить |
|---|---|---|
| производные свечи (5…1440) | `market_candle` timeframe=1 | да, полностью |
| `market_metric_hour` (OI, спред, глубина по часам) | `market_snapshot` | да, но только пока снапшоты не ротировались (90 дней) |
| минутные свечи | API биржи | да, если биржа отдаёт историю |
| фандинг | API биржи | обычно да |
| снапшоты (стакан, спред, глубина, OI на момент) | — | **нет, никогда** |
| факт листинга/делистинга в момент времени | — | **нет, никогда** |

Первые четыре строки — вопрос времени и нагрузки. Последние две существуют
только потому, что мы их записали в ту минуту; если не записали — их нет ни у
кого. Поэтому при выборе «чинить производное сейчас или дать сборщикам работать»
приоритет всегда у сборщиков.

## 2. Роллап: производные свечи и часовая микроструктура

### Как он понимает, где остановился

`collector_status.watermark_at` — «докуда обработан источник». Не путать с
`last_success_at` — «когда проход последний раз закончился». Джоб берёт кусок
`[watermark − 10 мин, watermark + 30 мин)`, дописывает знак только когда всё в
куске легло, и на следующем витке идёт дальше. Упавший проход знак не двигает и
повторяет тот же кусок.

### Добивка = отмотать знак назад

Это и есть штатная стратегия починки: **не самописный SQL, а тот же боевой код**,
которому просто говорят начать раньше.

```sql
-- посмотреть, где он сейчас
select watermark_at, last_success_at, consecutive_failures, last_duration_ms
  from collector_status where collector = 'rollup';

-- отмотать (пример: на начало повреждённого дня)
update collector_status set watermark_at = timestamptz '2026-09-02 08:55:00+00'
 where collector = 'rollup';

-- вернуть в живой режим, не досчитав
update collector_status set watermark_at = now() where collector = 'rollup';
```

Что он при этом пересчитает: производные свечи всех настроенных таймфреймов за
затронутые окна и часы `market_metric_hour` целиком.

### Сколько это стоит (замерено на проде 2026-09-02, 1482 инструмента)

* обычный живой проход, все шесть таймфреймов — **8.6 с**;
* проход в режиме догона (30 минут задолженности + 2 часа снапшотов на часовой
  этап) — **36–82 с**;
* скорость хождения — примерно **30 минут данных за 90 секунд**, то есть сутки
  задолженности ≈ **час** реального времени.

Пока он ходит по прошлому, производные свечи за настоящее отстают. Сбор минуток,
снапшотов, глубины и фандинга при этом идёт как обычно — отстаёт только
производный слой. Отсюда правило: **добивку делать в тихое время и не дольше, чем
не жалко отставания в UI.**

### Ограничения

* Часы старше ротации `market_snapshot` (90 дней) не восстановятся — исходников
  уже нет. Проверять `select min(received_at) from market_snapshot` перед тем,
  как отматывать далеко.
* Отмотка на самое начало данных = полный пересчёт истории. Для двух суток это
  час; для полугода это не «добивка», а отдельная задача с окном обслуживания.

## 3. Диагностика: как понять, что данные врут

### Роллап встал

```sql
select collector, consecutive_failures, last_duration_ms,
       round(extract(epoch from now() - watermark_at) / 60) as lag_min
  from collector_status where collector = 'rollup';
```
`lag_min` растёт и не падает — джоб не успевает или падает. `last_duration_ms`
около таймаута (180 000) — упирается в него.

### Часы посчитаны по огрызку

Самая коварная поломка: строка есть, выглядит нормально, а посчитана по паре
замеров вместо часа. Ловится только сравнением с источником:

```sql
select m.hour_time,
       round(avg(m.snapshot_count)) as stored,
       (select round(count(*)::numeric / nullif(count(distinct s.exchange_instrument_id), 0))
          from market_snapshot s
         where s.received_at >= m.hour_time
           and s.received_at <  m.hour_time + interval '1 hour') as actual
  from market_metric_hour m
 where m.hour_time > now() - interval '48 hours'
 group by m.hour_time order by m.hour_time;
```
`stored` заметно меньше `actual` — час посчитан по огрызку. Норма сейчас — 60
снапшотов в час на инструмент.

### Что душит базу прямо сейчас

```sql
select pid, now() - query_start as dur, state,
       left(regexp_replace(query, '\s+', ' ', 'g'), 120)
  from pg_stat_activity
 where state = 'active' and now() - query_start > interval '5 s'
 order by 2 desc;
```

## 4. Уроки, которые стоили простоя

* **Проход, который не успевает, обязан уметь откусывать.** Иначе отставание
  само себя кормит: не влез в таймаут → прогресс не записан → в следующий раз
  задолженность та же плюс интервал. Четыре часа так не отрабатываются никогда.
  (2026-09-02, роллап лежал с 16:22.)
* **«Когда закончил» ≠ «докуда дошёл».** Пока проход укладывается в интервал,
  разницы нет; в аварии она решает всё. Прогресс нужен отдельным полем.
* **Пересчёт, который перезаписывает целое огрызком, хуже, чем непересчёт.**
  Часовые агрегаты читались от `since` и затирали полный час фрагментом. Строка
  оставалась на месте, счётчик молчал, а «средний спред за час» был усреднён по
  одному замеру. Любой пересчёт окна обязан читать окно целиком.
* **Перезапуск, который «лечит», прячет болезнь.** Старый роллап держал знак в
  памяти и после рестарта пересчитывал всё с эпохи. Это чинило часы побочным
  эффектом — и маскировало то, что штатный путь их портит.
* **Упавший цикл не должен выглядеть как простаивающий.** Задача сервисного
  цикла, которую никто не ждёт, умирает молча: три часа роллапа не было, а
  дашборд показывал «0 failing».
* **Номер миграции брать из `git pull` прямо перед созданием файла.** Номер,
  выданный в задании заранее, столкнётся с чужим. (Коллизия 0012, мигратор упал,
  хаб стоял ~10 минут.)
